# Lotto Analysis 사용자 매뉴얼

이 문서는 Lotto Analysis를 직접 실행하고, 데이터를 갱신하며, 통계·번호 생성·백테스트 화면을 올바르게 활용하는 방법을 설명한다.

이 프로그램은 당첨번호 예측기가 아니다. 과거 공식 기록을 탐색하고, 사용자가 정한 조건으로 무작위 후보를 만들며, 생성 전략을 동일한 조건에서 비교하는 개인 분석 도구다.

## 1. 가장 간단한 사용 순서

평소에는 다음 순서만 기억하면 된다.

1. PostgreSQL을 실행한다.
2. FastAPI를 실행한다.
3. Next.js를 실행한다.
4. 브라우저에서 `http://localhost:3000`을 연다.
5. 대시보드에서 최신 회차와 누락 여부를 확인한다.
6. 분석 화면을 살펴보고 필요한 경우 후보 조합을 생성한다.
7. 사용이 끝나면 실행 중인 서버를 종료한다.

새 당첨 회차가 발표된 뒤에는 데이터 갱신 절차를 먼저 수행한다.

## 2. 프로그램 시작하기

모든 명령은 프로젝트 폴더 `/Users/lee/lotto-analysis`를 기준으로 한다.

### 2.1 최초 도구 확인

처음 실행할 때 Node.js와 pnpm이 설치되어 있는지 확인한다.

```bash
node --version
pnpm --version
```

Node.js는 20.9 이상이 필요하다. macOS에서 두 명령 중 하나를 찾지 못하면 Homebrew로 설치한다.

```bash
brew install node pnpm
hash -r
node --version
pnpm --version
```

프런트엔드 의존성은 최초 한 번 또는 `frontend/pnpm-lock.yaml`이 변경됐을 때 설치한다.

```bash
cd /Users/lee/lotto-analysis/frontend
pnpm install
```

### 2.2 PostgreSQL 시작

첫 번째 터미널을 열고 실행한다.

```bash
cd /Users/lee/lotto-analysis
docker compose up -d postgres
docker compose ps
```

`postgres` 서비스가 실행 중이면 준비된 상태다. Docker Desktop이 꺼져 있다면 먼저 실행한다.

### 2.3 FastAPI 시작

두 번째 터미널을 열고 실행한다.

```bash
cd /Users/lee/lotto-analysis
source .venv/bin/activate
uvicorn lotto_analysis.api.main:app --reload
```

다음 주소로 상태를 확인할 수 있다.

- API 상태: `http://127.0.0.1:8000/api/health`
- API 문서: `http://127.0.0.1:8000/docs`

상태 응답이 `{"status":"ok"}`이면 FastAPI가 정상 실행 중이다.

### 2.4 Next.js 사용자 화면 시작

세 번째 터미널을 열고 실행한다.

```bash

```

브라우저에서 `http://localhost:3000`을 연다.

Next.js와 FastAPI 연결 상태는 `http://localhost:3000/api/health`에서도 확인할 수 있다. 정상일 때 HTTP 200과 `status: ok`가 반환된다.

## 3. 새 회차 데이터 갱신

새 회차 발표 후에는 프로젝트 폴더에서 Python 가상환경을 활성화하고 다음 순서로 실행한다.

```bash
cd /Users/lee/lotto-analysis
source .venv/bin/activate
lotto-analysis collect-incremental
lotto-analysis collect-missing
lotto-analysis process
lotto-analysis db-import
lotto-analysis db-verify
```

각 명령의 의미는 다음과 같다.

| 명령 | 역할 |
| --- | --- |
| `collect-incremental` | 현재 저장된 마지막 회차 다음부터 최신 완료 회차까지 수집한다. |
| `collect-missing` | 과거 범위 안에서 없거나 유효하지 않은 회차를 보완한다. |
| `process` | 원본 전체를 검증하고 정제 CSV를 다시 만든다. |
| `db-import` | 정제 CSV를 PostgreSQL에 동기화한다. 같은 회차가 중복 저장되지 않는다. |
| `db-verify` | CSV와 PostgreSQL의 회차 및 기본 분석 결과가 같은지 확인한다. |

갱신 후 대시보드에서 다음 두 가지를 확인한다.

- 최신 회차가 공식 발표 회차와 같은가?
- 누락 회차가 0개인가?

수집을 중간에 중단해도 같은 명령을 다시 실행하면 유효한 기존 원본은 건너뛰고 이어서 진행한다.

## 4. 화면별 활용 방법

### 4.1 대시보드 `/`

프로그램을 열었을 때 가장 먼저 확인하는 화면이다.

- 최신 회차와 당첨번호
- 저장된 전체 회차 수
- 누락 회차 수
- 최근 8회 기록
- 최근 100회 출현 횟수 상위 번호

출현 횟수 상위 번호는 최근 과거 기록의 요약일 뿐, 다음 회차에 나올 가능성이 더 높다는 뜻이 아니다.

### 4.2 회차 기록 `/draws`

과거 공식 결과를 확인할 때 사용한다.

- 최신순 회차 목록 탐색
- 특정 회차 당첨번호와 보너스 번호 확인
- 1등 당첨자 수, 1인당 당첨금과 판매금액 확인
- 이전·다음 회차 이동

특정 회차 주소는 `/draws/회차번호` 형식이다. 예를 들어 1232회는 `/draws/1232`다.

### 4.3 기본 통계 `/analysis`

번호별 출현 기록과 조합의 전반적인 모양을 살펴본다.

- 최근 50·100·200·500회 또는 전체 회차 선택
- 시작·끝 회차 직접 지정
- 시작·끝 날짜 직접 지정
- 번호별 일반·보너스 출현 횟수
- 번호 합계의 평균·중앙값·범위
- 연속번호가 포함된 회차 비율
- 마지막 출현 이후 지난 회차 수

처음에는 `최근 100회`와 `전체 회차`를 각각 확인하는 것을 권장한다. 최근 범위만 보면 일시적인 우연을 장기 추세로 오해하기 쉽다.

### 4.4 기간 비교 `/analysis/compare`

최근 기간을 직전의 같은 길이 또는 전체 기간과 비교한다.

- 번호별 회차당 출현률 차이
- 기간별 순위 변화
- 최근 기록과 기준 기록의 차이

값이 증가했다는 것은 선택한 최근 기간에 상대적으로 더 자주 관찰됐다는 뜻이다. 다음 회차에서도 증가한다는 의미는 아니다.

### 4.5 출현 간격 `/analysis/gaps`

각 번호가 과거에 어느 정도 간격으로 등장했는지 확인한다.

- 평균·중앙 출현 간격
- 최소·최대 간격
- 최근 간격
- 현재 미출현 회차 수

오랫동안 나오지 않은 번호가 곧 나와야 한다고 판단해서는 안 된다. 추첨은 이전 미출현 기간을 보상하지 않는다.

### 4.6 패턴 분석 `/analysis/patterns`

개별 번호보다 조합 전체의 형태를 확인한다.

- AC 값 분포
- 인접 번호 간격
- 소수·합성수·제곱수 개수
- 번호 합계 구간
- 끝수 합계

후보 조합을 만들 때 지나치게 극단적인 조건을 피하고 싶다면 참고할 수 있다. 흔한 형태가 당첨 확률이 더 높다는 의미는 아니다.

### 4.7 번호 관계 `/analysis/relationships`

과거 회차에서 번호들이 함께 나타난 기록을 탐색한다.

- 자주 함께 나온 번호쌍과 3개 조합
- 기준 번호와 함께 나온 번호
- 번호 사이 거리
- 같은 끝수와 연속번호 관계
- 이전 회차와의 중복

동반 출현률은 선택한 과거 자료의 관계다. 두 번호를 함께 선택하면 미래 당첨 가능성이 높아진다는 뜻이 아니다.

### 4.8 7×7 행렬 `/analysis/matrix`

1~45를 고정된 위치에 배치해 공간적으로 분포를 살펴본다.

- 번호별 출현 횟수와 비율
- 행·열 합계
- 대각선 통계
- `/analysis/matrix/compare`에서 직전 기간과 최근 기간 비교

색상은 선택한 기간 안의 상대적 크기다. 추천 점수로 해석하지 않는다.

### 4.9 과거 조합 유사도 `/analysis/similarity`

서로 다른 과거 회차가 몇 개의 번호를 공유했는지 확인한다.

- 공통 번호 0~6개 분포
- 회차별 최대 중복 수
- 가장 유사했던 과거 회차
- Jaccard 유사도

내 후보가 과거 당첨 조합과 얼마나 비슷한지 이해하는 참고 자료로 사용할 수 있지만, 비슷하거나 다르다는 이유로 당첨 가능성이 달라지는 것은 아니다.

## 5. 후보 번호 생성 `/generate`

사용자가 정한 조건을 만족하는 무작위 후보 조합을 생성한다.

### 5.1 처음 사용할 때 권장 설정

- 전략: 균등 무작위
- 생성 개수: 5개
- 반드시 포함·제외: 비워두거나 꼭 필요한 번호만 입력
- 홀수 개수: 2~4개
- 낮은 번호 개수: 2~4개
- 번호 합계: 100~180
- 과거 당첨 조합과 완전히 같은 결과 제외: 선택
- 후보 결과끼리 최대 중복: 3~4개
- seed: 일상 사용은 비워두고, 결과 재현이 필요하면 숫자 입력

처음부터 조건을 많이 추가하지 않는 것이 좋다. 조건이 많다고 더 좋은 번호가 되는 것이 아니라 가능한 후보의 수만 줄어든다.

### 5.2 균등 무작위와 빈도 가중

- `균등 무작위`: 조건을 통과하는 번호를 기본적으로 균등하게 선택한다.
- `과거 빈도 가중`: 과거 출현 횟수를 제한된 가중치로 사용한다.

빈도 가중은 실험할 수 있는 다른 생성 방식일 뿐 균등 전략보다 당첨 확률이 높다는 의미가 아니다.

### 5.3 seed 사용법

같은 데이터, 조건과 seed를 사용하면 같은 결과를 재현할 수 있다.

seed는 다음 상황에 유용하다.

- 나중에 같은 후보를 다시 확인할 때
- 전략을 동일한 조건으로 비교할 때
- 백테스트 결과를 재현할 때

실험 목적이라면 사용한 조건과 seed를 함께 기록한다.

### 5.4 일부 조합만 생성됐을 때

요청 개수보다 적은 결과가 나오면 조건이 서로 충돌하거나 지나치게 좁을 가능성이 크다.

다음 순서로 완화한다.

1. 포함·제외 번호 충돌을 확인한다.
2. 합계와 홀짝 범위를 넓힌다.
3. 후보끼리 최대 중복 제한을 넓힌다.
4. 과거 조합 최대 중복 제한을 넓힌다.
5. 최대 시도 횟수는 마지막에 조정한다.

## 6. 백테스트 활용

### 6.1 단일 전략 백테스트 `/backtests`

과거의 각 목표 회차 직전까지만 학습 데이터로 사용해 후보를 생성하고 실제 당첨번호와의 일치 수를 확인한다.

첫 실행은 기본값을 권장한다.

- 목표: 최근 20회
- 회차당 후보: 5조합
- 전략: 균등 무작위
- 기본 seed: 기록 가능한 숫자

그다음 같은 목표 수·후보 수·seed를 유지하고 빈도 가중 전략으로 바꿔 비교한다.

### 6.2 반복 전략 비교 `/backtests/experiment`

여러 seed와 조합 수를 사용해 균등·전체 빈도·최근 빈도 전략을 같은 조건에서 반복한다.

결과를 볼 때 다음을 구분한다.

- 전체 생성 조합의 일치 분포
- 각 목표 회차에서 가장 잘 맞은 조합의 분포
- 완료 실행 수
- 동일한 조합 수 안에서의 전략 차이

조합을 많이 생성할수록 최고 일치 수가 자연스럽게 높아진다. 따라서 1조합 결과와 10조합 결과의 최고값을 전략 성능처럼 직접 비교하면 안 된다.

백테스트는 코드와 전략의 동작을 과거 자료에서 비교하는 도구다. 좋은 과거 결과가 미래 성과나 실제 당첨 확률 향상을 보장하지 않는다.

## 7. 권장 주간 사용 루틴

새 회차가 발표된 뒤 다음 흐름을 권장한다.

1. `collect-incremental`과 `collect-missing`을 실행한다.
2. `process`, `db-import`, `db-verify`를 순서대로 실행한다.
3. 대시보드에서 최신 회차와 누락 0개를 확인한다.
4. 최근 100회와 전체 기본 통계를 비교한다.
5. 필요하면 기간 비교·패턴 화면을 참고한다.
6. 너무 많은 조건을 넣지 않고 후보 5~10개를 생성한다.
7. 실험할 경우 조건, 전략과 seed를 기록한다.
8. 일정 기간이 쌓이면 같은 조건으로 반복 백테스트를 실행한다.

지난 결과에 맞춰 매주 규칙을 바꾸면 전략을 일관되게 평가하기 어렵다. 비교 목적이라면 일정 기간 같은 규칙을 유지한다.

## 8. 올바른 해석 원칙

다음 표현은 서로 다르다.

| 화면에서 확인한 사실 | 잘못된 해석 |
| --- | --- |
| 최근 100회에서 많이 출현했다. | 다음 회차에도 나올 가능성이 높다. |
| 오랫동안 출현하지 않았다. | 이제 나올 차례다. |
| 두 번호가 과거에 자주 함께 나왔다. | 앞으로도 같이 나올 가능성이 높다. |
| 특정 전략의 과거 평균이 높았다. | 그 전략이 미래에도 유리하다. |
| 과거 조합과 많이 겹친다. | 좋은 조합 또는 나쁜 조합이다. |

이 프로젝트의 올바른 목적은 다음 세 가지다.

- 공식 기록을 정확하고 편리하게 탐색한다.
- 감으로 정한 조건을 명시적이고 재현 가능한 규칙으로 바꾼다.
- 여러 생성 전략을 미래 데이터 누수 없이 같은 조건에서 비교한다.

## 9. 프로그램 종료

FastAPI와 Next.js를 실행한 각 터미널에서 `Ctrl+C`를 누른다.

PostgreSQL을 중지하되 저장 데이터는 유지하려면 프로젝트 폴더에서 실행한다.

```bash
docker compose stop postgres
```

또는 컨테이너를 제거하되 DB 볼륨을 유지하려면 다음을 사용한다.

```bash
docker compose down
```

`docker compose down --volumes`는 PostgreSQL 데이터까지 삭제하므로 초기화가 확실히 필요한 경우가 아니면 사용하지 않는다.

## 10. 문제 해결

### `zsh: command not found: pnpm`이 표시될 때

Node.js 또는 pnpm이 설치되지 않았거나 현재 터미널의 명령 경로에 반영되지 않은 상태다.

```bash
brew install node pnpm
hash -r
node --version
pnpm --version
```

두 버전이 정상적으로 출력되면 프런트엔드 폴더에서 의존성을 확인하고 다시 실행한다.

```bash
cd /Users/lee/lotto-analysis/frontend
pnpm install
pnpm dev
```

### 화면에 “분석 서버를 기다리고 있어요”가 표시될 때

1. FastAPI 터미널이 실행 중인지 확인한다.
2. `http://127.0.0.1:8000/api/health`를 연다.
3. PostgreSQL 상태를 `docker compose ps`로 확인한다.
4. `http://localhost:3000/api/health`를 확인한다.

### PostgreSQL 비밀번호 인증이 실패할 때

`.env`의 `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`와 DB 도구의 연결 정보를 동일하게 입력했는지 확인한다. 이미 생성된 PostgreSQL 볼륨은 `.env`의 새 비밀번호만 바꿔도 자동 변경되지 않는다.

### 최신 회차가 보이지 않을 때

다음 순서를 다시 실행한다.

```bash
lotto-analysis collect-incremental
lotto-analysis collect-missing
lotto-analysis process
lotto-analysis db-import
lotto-analysis db-verify
```

그 후 브라우저를 새로고침한다.

### 번호 생성이 완료되지 않을 때

오류 메시지와 조건별 제외 횟수를 확인하고 포함·제외 충돌, 합계·홀짝 범위와 중복 제한부터 완화한다.

### 포트가 이미 사용 중일 때

기존 FastAPI 또는 Next.js 실행 터미널이 남아 있는지 확인한다. 기존 프로세스를 종료한 뒤 다시 실행하는 것이 가장 단순하다.

### 더 자세한 운영 정보가 필요할 때

- 반복 확인 작업: [사용자 체크리스트](USER_CHECKLIST.md)
- Next.js 상태 점검과 오류 로그: [Next.js 운영 안내](NEXTJS_OPERATIONS.md)
- 전체 설치·CLI 명령: [프로젝트 README](../README.md)

## 11. 안전하고 현실적인 사용 원칙

번호 생성 결과는 구매 권유나 당첨 추천이 아니다. 구매한다면 미리 정한 소액 예산 안에서 오락 목적으로만 사용하고, 손실을 만회하기 위해 구매 금액을 늘리지 않는다.

통계 분석은 선택 과정을 정리하고 실험을 재현하는 데 도움을 줄 수 있지만, 무작위 추첨의 미래 결과를 알아내지는 못한다.
